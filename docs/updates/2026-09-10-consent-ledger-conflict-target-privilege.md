# The consent ledger's conflict target required a privilege the role must not have

**10 September 2026.** `api/_lib/consent-ledger.mjs`, one line.

Assume no repository access and no memory of previous conversations.

## What was wrong

The append-only consent ledger went live on a Vercel **preview** deployment for
the first time. Every submission failed. The lead was stored, the operator
evidence was written, and the `cst_*` consent grant was withheld — which is the
designed fail-closed behaviour — but no row ever reached the ledger.

The statement `appendConsentEvents()` sent was:

```sql
INSERT INTO communication_consent_events (occurred_at, channel, …)
VALUES ($1, …, $13), ($14, …, $26)
ON CONFLICT (dedupe_key) DO NOTHING
```

Postgres refused it with **SQLSTATE `42501`, `insufficient_privilege`** —
`permission denied for table communication_consent_events`.

The application role, `consent_ledger_app`, holds `INSERT` and nothing else.
That is deliberate and is the ledger's central security property: append-only is
a database grant, not a code convention, and a leaked `CONSENT_LEDGER_URL` must
not be able to enumerate the phone numbers and consent decisions the table
holds. Reading the ledger is an owner-credential job, performed off Vercel.

**Naming a conflict target makes Postgres require `SELECT` on the table.**
Inferring which unique index arbitrates the conflict is a read. `INSERT` alone
is not enough.

This had been verified by hand and still got through. The manual verification
ran a plain `INSERT`, which succeeds under an `INSERT`-only role. The clause the
code adds was never executed against the real grant, and every automated test
ran behind an injected executor seam that never parses SQL. The gap was exactly
the one the implementation document had flagged as unproven — "not that the
`ON CONFLICT` clause matches the real unique index" — and it was the defect.

## Why it took three sessions to see

`ledgerLogShape()` deliberately discarded the driver's error, on the correct
grounds that a Postgres error message routinely carries the host, the role and
sometimes the parameter values. The operator log therefore said only
`CONSENT_LEDGER_APPEND_FAILED`, which cannot distinguish a missing dependency
from an unreachable host from a refused credential from a refused statement.

That was fixed first, in a separate change: `ledgerLogShape()` now also emits
`ledger_driver_error` (the error class name) and `ledger_driver_code` (a
symbolic code or SQLSTATE), each whitelisted by `driverShape()` to a
letter-initial identifier or five SQLSTATE characters. No message, cause object
or stack is read, and a value that fails the pattern is dropped rather than
logged. The very next preview submission logged:

```json
{"event":"lead.consent.ledger_failed",
 "ledger_error":"CONSENT_LEDGER_APPEND_FAILED",
 "ledger_driver_error":"NeonDbError",
 "ledger_driver_code":"42501"}
```

Which named the cause immediately. **A fail-closed path that cannot say why it
closed costs more than the failure it prevents.**

## What was measured

A throwaway PostgreSQL 16 cluster, `db/001_communication_consent_events.sql`
applied verbatim, role granted `INSERT` and nothing else, statement generated by
the real `buildInsert()`:

| Statement | Result |
|---|---|
| plain multi-row `INSERT` | `INSERT 0 2` |
| `… ON CONFLICT (dedupe_key) DO NOTHING` | **`ERROR 42501`** |
| `… ON CONFLICT ON CONSTRAINT <name> DO NOTHING` | **`ERROR 42501`** |
| `… ON CONFLICT DO NOTHING` | `INSERT 0 2` |
| `… ON CONFLICT DO NOTHING` replayed | `INSERT 0 0` |
| replayed after the owner deleted one of the two rows | `INSERT 0 1` |

Naming the constraint explicitly does **not** avoid the requirement. Adding
column-level `GRANT SELECT (dedupe_key)` does make the targeted form work, and
was rejected — see below.

## What changed

One line in `api/_lib/consent-ledger.mjs`:

```diff
-    "ON CONFLICT (dedupe_key) DO NOTHING";
+    "ON CONFLICT DO NOTHING";
```

with a comment recording why the more readable form is unavailable, so it is not
"tidied" back.

**The database did not change.** No new migration, no new grant, no edit to
`db/001` — which must stay byte-identical to what was applied, because its worth
as a record depends on that. The provisioned Neon instance remains exactly as it
was verified.

## The resulting contract

Every documented property of the append survives, and each was re-verified
against a real Postgres rather than asserted:

- **A statement failure cannot half-write the two new rows.** One statement, one
  transaction: both commit or neither does.
- **`DO NOTHING` is evaluated per row.** A replay against a ledger holding one
  of the two rows no-ops that row and inserts the missing one, converging on the
  complete pair rather than leaving the gap forever.
- **A fully duplicated replay inserts nothing and succeeds.**
- **`SELECT`, `UPDATE`, `DELETE` and `TRUNCATE` remain refused** to the
  application role under the new statement, with `42501`.

What the change costs, stated plainly: an untargeted `DO NOTHING` also absorbs a
**primary-key** collision instead of raising, so such a row would be dropped and
reported as already recorded rather than failing closed. `event_id` is a v4 UUID
minted by Postgres, so this is not a practical concern — but it is a real
difference, and there is no `INSERT`-only form that avoids it. The alternative
was worse.

## The alternative that was rejected

`GRANT SELECT (dedupe_key) ON communication_consent_events` — column-level, so
narrower than table-wide `SELECT` — does make the targeted form work. It was
rejected because a `dedupe_key` is
`website:<submission_id>:<channel>:<event_type>`, so read access to that one
column lets the credential enumerate every consent decision ever recorded,
by submission. It carries no phone numbers, which is why it is tempting. It
still hands an enumeration of the ledger to a credential that lives in Vercel,
which is the precise thing the `INSERT`-only tightening existed to prevent, and
it would have required a second migration against the append-only table.

**If a future change wants a conflict target back, the answer is not to grant
`SELECT`.**

## Tests

`tests/consent-ledger.test.mjs`, 34 tests, all passing. `npm run check` passes.
`tests/consent.test.mjs` and `tests/consent-state.test.mjs` pass unchanged.

The new regression test asserts the statement carries no conflict target, no
`ON CONSTRAINT`, no `DO UPDATE` (which would need `UPDATE`) and no `RETURNING`
(which would need `SELECT`), and carries the measured table above as its
rationale. It is a static assertion on the generated SQL: the suite still never
reaches a database.

**Tests passing does not mean this works in production.** The proof that it
works is a preview submission producing two ledger rows, which had not happened
when this was written.

- `COMMUNICATIONS_CONSENT_ENABLED` remains **absent from Vercel Production**.
  Production is unchanged and shows no consent tick boxes.
- `CONSENT_LEDGER_URL` exists **in Preview only**.
- No successful append from application code has yet been observed.
- No `CONSENT LEDGER: RECORDED` row has been rendered in HubSpot, because the
  preview has no HubSpot credential; the endpoint returns 503 after the append.
- No SMS has been sent and no call placed.
- The owner/admin database credential has never been placed in Vercel.
